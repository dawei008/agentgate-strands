# 用户视角自查清单（由真实抱怨提炼，不是从原则推导）

> 每一条都有出处：左边是用户的原话，右边是从那句话里提出来的规则。
> **不许往这张表里加没有抱怨来源的条目** —— 那样它会变成又一份「设计原则」，
> 而这张表存在的理由恰恰是：原则读起来都对，抱怨才指得出哪一条没做到。

清单的用法是**五道闸**（用户 2026-08-24 认可的顺序）：

| 闸 | 时机 | 做什么 |
| --- | --- | --- |
| ① | 做之前 | 低保真 mock 先给用户看，路线由用户选，不由我选 |
| ② | 设计时 | 约定优先；要发明一种新做法，得给出理由 |
| ③ | 设计时 | **拿用户的句子当验收**：句子里没出现的概念，动线里不许出现 |
| ④ | 做完后 | 冷启动自查：只看截图，不看代码，试着把任务走完 |
| ⑤ | 长期 | 抱怨 → 成文规则 → 能钉的钉成测试（就是本文件） |

## 1. 有通用控件就用通用控件

> 「一般情况下不都是选是通过打勾的方式去选吗？如果选错了，去掉勾再重新选就行了。」

对比页的候选行原本是 `<button aria-pressed>`：看起来选中了，但它不是勾选框。
**用户对通用控件已有的预期（怎么取消、怎么多选、键盘怎么走）全部落空**，
而自造控件必须把那些预期一件件重新实现 —— 通常只实现了一半。

**钉法（已钉）**：`web/tests/compare-page.test.tsx:338`
「选择走真的勾选框：勾上=选中、去掉勾=取消（不是 aria-pressed 的按钮）」——
`toBeChecked()` 只对真 checkbox/radio 成立 ⇒ 换回按钮它会红。
⚠️ 两种控件在「看起来选中了」上同形，这条断言是唯一分得出它们的地方。

## 2. 不许静默改动用户的选择

> （同一条抱怨的下半句）「如果选错了，去掉勾再重新选就行了。」

原实现选满两条后，点第三条会**静默挤掉最早那条** —— 用户没取消过的选择凭空消失。
更坏的是替代方案「点了没反应」：它与「这一行不能选」在屏幕上同形。
正解是**可见地 disabled + 一句说明为什么**：读起来是规则，不是页面坏了。

**钉法（已钉）**：`compare-page.test.tsx:425`
「选满两条 → 第三条的勾选框 disabled + 卡头说出为什么；去掉一个勾就又能选」。
两半都钉：能不能勾、以及**有没有话**。

## 3. 内容量决定容器（超过一屏的长文就别用浮层）

> 「评估报告抽屉式看着太费劲，很多字但只有一半屏幕能看，除非抽屉式默认更大区域或可调。」

先只治了宽度（600 → 1080），抱怨没消 —— 因为抱怨的对象是**形制**。
详见 [ADR 0013](adr/0013-long-form-lives-on-a-page.md)。

**钉法：不可机械钉，靠 ADR + 本条自查。** 说清为什么不可钉：判据是「内容量」与
「读 vs 填」，两者都不是 DOM 里的量。⚠️ 别拿「报告页路由存在」当这条的守卫 ——
那只证明页面在，证明不了下一个长文面没有被塞进抽屉。

## 4. 区分必须对称，不能靠「有 / 没有」去推

> 「对比的结果也看不太清，其实可以用不同的颜色标示哪些是第一轮，哪些是第二轮。」

原实现只有右栏带 accent 描边，左栏什么都没有。**缺陷不是「缺颜色」而是「不对称」**：
「哪栏是新的」得靠「有描边 vs 没描边」去推，而正文每一处并排格里连那道描边都没有。
两侧都要有自己的身份，且每处颜色旁边配四个字（「上一次 / 这一次」）——
灰度与色觉差异下要有等价读数。
⚠️ 身份色只上到壳，**绝不上到分数**：绿分数读作「达标」，绿栏读作「这一次」。

**钉法（已钉）**：`compare-page.test.tsx:468`
「两栏身份色：选满才上色，且色只落在壳上 —— 分数列一格都不许染」。
那支测试故意**先点 V3 再点 V1**，以证明身份跟时间不跟点击顺序
（按顺序点的话，两种实现给出同一个结果，测不出差别）。

## 5. 动线属于用户的对象，不属于系统的容器

> 「我打开某个 run 的报告，看完了要回运行列表；如果这份报告有意思，我把链接发给同事，
> 他点开看到的是同一份。」（Gate ③ 的验收句）

句子里的对象只有 **run**，没有「方案」⇒ 报告路由就只带 run_key，方案 id 从
run_key 前缀现推、不进 URL。同理，跨版本对比原本锚在「一个方案内部」，
而用户说的是「选不同的 run 做对比」⇒ 对比独立成页、候选池跨方案。

**钉法（半钉）**：10 支测试文件都用**裸 run_key** 挂载 `ReportPage`
（`web/tests/plan-version-labels.test.tsx:142` 的 `renderReport` 注释写明理由），
对比页有深链往返测试。
⚠️ 这钉住的是「现在的路由长这样」，钉不住「下一个面别把容器塞进 URL」——
那半仍是自查。

## 提炼时的两个陷阱（踩过，写下来）

1. **别把实现形态写成「已定形制」**。本清单第 3 条的 issue 档里，我曾把
   「抽屉式是已定形制」写进 Out of scope —— 而用户抱怨的就是那个形制。
   拿现有实现去限制用户能选什么，是把闸 ① 作废掉。
2. **一条抱怨常含两条规则**，别只提炼听起来更像设计问题的那一条。
   「打勾」那句话同时给出了第 1 条（控件类型）与第 2 条（选择不许被静默改动）；
   只做第 1 条会留下静默挤掉的行为，只做第 2 条会留下一个自造控件。
