# ADR-0016: Agent 是主语——详情页按「观测 → 评估 → 优化」闭环组织，计划是工具、run 是事件、分析是历史

日期：2026-09-03 · 状态：已采纳（用户「同意，按这个来设计」；同日修订为动词分区，用户「按现在的思路进行设计」）· 编号说明：0015 已随中国区 TS 改造套件撤下（`4df5f85`），不复用。

## 背景

现有顶栏按名词平铺：Agent / 评估器 / 数据集 / 评估计划 / 评估分析（+ 大屏）。用户 2026-09-03：
「设计思路有点乱……从一个 agent 评估的生命周期的角度，有没有更好的设计思路」。
症状：趋势同时长在评估计划详情（TrendCard）与评估分析；综合报告四段正往评估分析迁（ADR-0014）；
采纳按钮在报告里、版本标签在 Agent 详情、采纳效果在分析页——「改进」这一步被拆在三页。
根因：**主语错了**。真正随时间演化的是 Agent；评估计划只是量它的工具，run 是发生的事件，分析是它的历史。

## 生命周期（导航要顺着它走）

接入 → 备料 → 定计划 → 跑 → 读本次 → 看变化 → 改进（换版本）→ 再跑 …

## 更大的角度：三个动词是一个闭环

```
观测 ──▶ 评估 ──▶ 优化 ──▶ (换版本) ──▶ 观测 …
 发生了什么     好不好        改什么、改了有没有用
```

观测是事实层（不下判断），评估是判断层，优化是行动层且必须回到观测/评估闭环。
AgentGate 今天评估层强、优化层刚起步（ADR-0014 迁移）、观测层几乎没有（trace 只被当评估输入）。
**边界：AgentGate 不重做 APM。** 观测层要薄——只放「要不要评、要不要改」所需的几个数，
trace 级深挖一律深链 CloudWatch GenAI 可观测性仪表盘。差异化在于把观测**接到**评估与优化上。

## 决定

1. **Agent 详情 = 闭环枢纽**，按三个动词 + 设置分四区，顺序固定：
   ① **现状（观测）**：近 24h 会话量 / P95 / Agent 侧成本 / 空响应率 / 工具失败率（各一数 + 环比）、
      最近一次评估结果、跌破目标线的告警、下次运行时间、「在 CloudWatch 查看 trace」深链。
      数据源 = 已在拉的那批 span，**不建新基础设施**。
   ② **评估**：评估计划（环节、定时、预算、运行入口）+ 运行历史（跨计划全部 run，每条 → 运行报告，报告只讲本次，ADR-0014）。
   ③ **优化**：趋势（带版本变更竖线）+ **问题台账**。台账的单位是「问题」不是「段」：每条问题一行/一卡，
      横着走完闭环 —— 问题（证据引用）→ 根因 → 建议（具体修法，fix_type）→ 采纳（落到哪个版本）→ 效果
      （下一次 run 的前后对比）。「反复出现的问题 / 当前优先建议 / 改进采纳效果」三段散文**不再独立成块**：
      问题是行、建议是格、效果是格；「当前优先建议」= 建议格非空且采纳格为空的行按影响排序；没有建议的
      问题在建议格放「生成改进稿」入口；建议之间的依赖（「需与 X 一起判断」）要能表达。
      默认口径 = 最新一次 vs 上一次，任意两次对比是子模式。（用户 2026-09-03 二次修订：「少了下一步改进的
      建议，直接从问题到了改造效果」⇒ 因果链必须摆在同一行。）
      默认口径 = 最新一次 vs 上一次，任意两次对比是子模式。
   ④ **配置**：身份 / 版本标签 / 调用配置 / 探测。放最后。
2. **趋势只有一个家 = ③**。评估计划详情不再承载任何跨 run 内容。
3. **顶栏 = Agent / 评估计划 / 评估器 / 数据集 / 大屏**。「评估分析」从顶栏拿掉（术语不变，只是不再是导航入口）；
   「观测」「优化」不设独立入口——它们只对具体 Agent 有意义。大屏 = 舰队级观测；顶栏评估计划 = 舰队级评估排程看板。
4. **评估器 / 数据集**保留两个入口（用户 2026-08-29 的拆分不动），视觉上降一级为「资产」。
5. 报告页页脚「与上次对比」的门 → 跳该 Agent 的 ③，预选本次为「这一次」。

## 分数口径修订：决策看「每个评估器过不过线」，不看合成均分（用户 2026-09-03 三次修订）

- 现状：`overall_mean` = 各评估器均分再平均（`planrun.py:248`）。第 2 层（同一评估器跨会话平均）成立；第 3 层把不同评估器
  （回答完整性 / 事实一致性 / 语气合规 / 工具调用正确率…）平均是苹果加桔子——均分 0.86 ▲ 可以盖住某一个评估器连续四轮未过线。
  加权平均不采用（权重 = 没人能复核的发明阈值）。
- **③ 优化的头部 = 评估器面板**：评估计划里配了几个评估器就列几行（N 动态，含线上评估评估器与回归测试评估器；红队用拦截率），
  每行 = 名称 · 本次分 · 较上一次 ▲▼ · 过/未过目标线（0.70，与告警同一条线）· 逐 run 小趋势；未过线的行高亮置顶。
  取代单条「线上评估均分」趋势图；`overall_mean` 退成参考（排序、排程看板、跨 Agent 粗比仍可用），不再出现在做决定的位置。
  数据已在每个 run 的环节摘要里（`summary[评估器].mean_score` / `evaluator_stats`），前端零后端依赖。
- **头部一句话** = 「N 个评估器 · M 过线 · <最差评估器名> <分> 未过」（首页舰队表与大屏的现状格同口径），不再是「0.86 ▲」。
- **问题台账来自各评估器**：每条问题标出它由哪些评估器的低分诊断产出（`synthesis_issues[].evaluators`，后端 additive 补字段），
  点评估器面板的一行 ⇒ 台账按该评估器过滤；台账行另带「本次新增 / 自 #N 持续 · K 次」标记（`first_seen_run` / `last_seen_run`）。
- CONTEXT.md「线上评估均分」词条保留定义，追加一句「决策位不用它」；这条修订随实现批一并落 CONTEXT。

## 舰队级（多 Agent）：同一个闭环抬一级，不加新名词（用户 2026-09-03 同日追加）

- **首页的视角是观测，不是评估**（用户 2026-09-03「现在首页全是从评估的角度出来做的，感觉不对」）：首页先回答
  「我有哪些 Agent、它们现在在线上跑得怎样」—— 每张卡以 Agent 的身份（名 / 版本 / runtime / 版本变更时间）和**观测五个数**
  （近 24h 会话量趋势、P95、成本、空响应率、工具失败率）为主体；评估（最近一次 M/N 过线、下次运行）和优化（未采纳 / 已验证）
  退成卡底两行状态。没被评估过的 Agent 在首页照样是一张完整的卡（观测数据都在，只是评估行写「未评估 · 新建评估计划」）。
  hero 带同理：舰队级观测（总会话量、总成本、P95 最差、异常率）在前，评估告警在后。待处理条混合两类：观测告警
  （工具失败率飙升 / 空响应率 / 成本超预算 / run 失败）与评估告警（评估器连续未过线）。数据源 = `agent_status`，字段已全。
- **首页 = Agent 总览 = 舰队现状表**，回答「现在哪个 Agent 需要我动手，为什么」：顶部告警条（跨 Agent：评估器连续未过线 /
  预算用尽 / 运行失败），下面每个 Agent 一行走完生命周期 —— 版本 · 现状（均分 ▲▼、告警数、24h 成本）· 评估（下次运行、最近结果）
  · 优化（未采纳数、已验证数）；每格深链到该 Agent 详情对应 Tab；默认按「最需要动手」排序；全部正常时告警条给一句中性现状。
  数据源 = `agent_status` 逐 Agent（或批量版），与 ① 现状同源。登录后落在这里；旧工作台的「最近运行」并入评估计划排程看板。
- **大屏 = 这张表的墙上模式**：同一份派生数据，自动轮播、大字、无交互；现有大屏自己那套派生逻辑并轨，不再两个「整体」各说各话。
- **顶栏两组**：主线 = Agent（首页）（「大屏」暂从顶栏拿掉，用户 2026-09-03「去掉大屏，先看 Agent」；墙上模式后续再接）；资产与排程 = 评估计划（排程看板：所有计划的定时、预算、本月花费、下次运行、最近结果）
  · 评估器（加「跨 Agent 表现」：多少 Agent 在用、各自均分、是否有 Agent 长期过不了它 —— 区分「Agent 差」与「尺子太严」）
  · 数据集（加「覆盖」）。资产与排程视觉上降一级。
- **舰队级优化不设页面**：单 Agent 问题台账落地后，在首页表下加一条「跨 Agent 共性问题」——同一根因（共用工具/知识库）在多个
  Agent 上出现只算一条，A 上采纳有效 ⇒ 对 B 提示同修法可用；采纳率、闭环时长在此聚合。

## 闭环上缺的两跳（差异化所在，后续批）

- **观测 → 评估的触发**：版本标签变更自动跑一次（「这次改动有没有退步」）；观测指标跌破线自动跑一次
  （「线上变差是不是 Agent 的问题」）。EventBridge Scheduler 机制已有，差触发条件。
- **综合报告结构化输出**（台账的数据前提）：`app/planrun.py` 的综合报告从四段散文改为结构化问题条目
  （问题 / 证据引用 / 根因 / 建议 / fix_type / 关联问题），Strands 诊断输出本就是这个形状；四段散文退为可选一句总结。
  前端在此之前用「散文 + proposals 对回」过渡。
- **优化 → 验证的自动判定**：采纳时记「预计影响的用例/指标」，下一次 run 完成后自动给「采纳后：case-9 仍失败 /
  事实一致性 0.74→0.85」。`adopted_at`、`refs` 已有，差验证那一跳。
